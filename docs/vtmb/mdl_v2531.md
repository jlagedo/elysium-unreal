# VtMB `.mdl` v2531 — struct map

The **skeletal half** — bones, sequences, the compressed animation tracks, skinning,
and attachments (for the `character/**` NPC models this parser raises on) — is
documented in `docs/vtmb/animation_and_movers.md`, Part A.

Authoritative layout for the VtMB studio-model format, transcribed from **VAMPTools**
(`$ELYSIUM_WORK_ROOT/research/reference-source/VAMPTools/MDLConverter`, atrblizzard) — the only VtMB-native parser. Its
`inc/external/studio.h` + `optimize.h` are hand-fitted to VtMB's disk format (the
author annotates every alignment fixup); `src/Mesh.cpp` is the reference walk that
produces correct FBX. Cross-checked by **Crowbar** (labels this format *"Source -
Vampire: The Masquerade - Bloodlines"*, version 2531).

**All offsets below are probe-verified** (`research/tooling/probes/probe_mdl.py`): headers,
materials, the mdl↔vtx lockstep walk, and all three vertex formats reconstruct valid
in-hull geometry with clean UVs on real scenery props (`pillars` 96 tris/unskinned,
`lampfloor` 1066 tris/skinned, `bookend` 530 tris/compressed). The header field
offsets are additionally **cross-confirmed against the game decompile** (`client.dll`
in Ghidra: `C_BaseAnimating::SetupBones` and its callees read `numbones@0xf0`,
`boneindex@0xf4`, `numlocalanim@0x108`, `localanimindex@0x10c`, bone stride `0xa0`,
`Flags@0x88`); the skeletal-animation decode (`docs/vtmb/animation_and_movers.md` Part A)
carries the same decompilation provenance.

## Files per model

A model is **2–3 sibling files** in the VPKs under `models/`:

| Ext | Role | Notes |
|---|---|---|
| `.mdl` | header + bones + materials + **embedded vertex data** | `IDST`, version **2531** |
| `.dx80.vtx` | strip/index data (triangle topology) → mesh-vertex IDs | the VtMB `.vtx` variant |
| `.phy` | vphysics collision (optional) | ~2/3 of models; **deferred** |

**Key divergences from modern Source (v44–49):**
- **No `.vvd`.** Vertex positions/normals/UVs are embedded *inside the `.mdl`*, per
  `StudioModel` (field `VertexIndex`). Modern Source splits them into `.vvd`.
- **`.vtx` is `.dx80.vtx` / `.dx7_2bone.vtx`**, never `.dx90.vtx`.
- **`MDLHeader.Name` is `char[128]`** (modern is `char[64]`), so `Length` sits at
  offset **140**, not 76. (Reading offset 76 lands mid-Name → the recon saw 0 there.)
  The widening is Troika's toolchain rather than this format: the compiled expression
  tables carry the same `char[128]` in place of Source's `char[64]`
  (`docs/vtmb/facial_animation.md` → "The compiled `.vfe` header").
- Structs carry extra padding vs. modern Source; the VtMB tool was compiled **x86**,
  so on-disk reserved space for runtime pointers is **4 bytes** each.

`Name` holds the model's own path **without a `models/` prefix and with forward slashes**
(`character/npc/unique/society_of_leopold/average_vampire_hunter/average_vampire_hunter.mdl`),
so a caller joining it against the install prepends `models/`. Across all 4,445 installed
v2531 headers the field is never full: the longest name is **89** characters and **50** are 64
or longer, so any reader that keeps only 64 bytes of it silently drops the terminator. Two
64-character prefixes are shared by distinct models —
`scenery/furniture/DiningTableOldBeachHouse/DiningTableOldBeachHo{use,use_new}.mdl` and
`character/npc/common/shopkeeper/Shopkeeper_China_town_Female/chi{na_town_Female01,na_town_Female02}.mdl`
— so a 64-byte field renders those pairs identically, and an identity join keys on `Checksum`
rather than on this field. Names are mixed case, though no two of the 4,445 differ only by
case, so a lowercased lookup against the install index resolves each to exactly one file.

### The loaded image is the file, patched in place

The engine loads the `.mdl` **whole and unrelocated**: the runtime `studiohdr` pointer is
the file image at offset 0, so `pointer − studiohdr` is a file offset directly. Measured on
one `sp_theatre` capture that retained all **141** distinct runtime studio headers and
compared each against the patch-first installed file carrying the same `Checksum`: every
one of the 141 `Length`@140 values equals the installed file size exactly, and **42** images
are byte-identical to disk.

The other 99 differ only in narrow, structured ranges — the loader writes into the image
rather than into a copy. In one complete run the whole difference is 26,958 bytes:

| Range | Bytes | Models | What |
|---|---:|---:|---|
| the include-model bone remap arrays | 24,234 | 27 | written on **exactly** the 27 models that carry include models and on no other, zero exceptions |
| `StudioBone.Flags`@136 | 743 | 27 | one byte per bone, at the 160-byte stride |
| `StudioMesh.VertexData`@24 | 258 | 51 | the 36-byte runtime struct reserved on disk |
| `StudioSeqDesc`+0xc..0xf | 170×4 | 49 | one dword per sequence descriptor |
| `StudioModelGroup`+0x4..0xc, +0x14..0x1b, +0x44..0x4b | ~41 each | 27 | inside the include-model records |
| `MDLHeader.NumLocalNodes`@280 | 58 | 58 | |
| `MDLHeader.Flags`@228 | 45 | 45 | |

### Which of those bytes an evaluation actually dereferences

The loader-written ranges above matter because a pointer captured at runtime is a file
offset, so a byte the loader rewrote is *not* the byte on disk. Two complete `sp_theatre`
runs resolve every fired contribution to the exact spans retail read, and the animation
path touches **3,449,152** and **3,474,414** bytes across **34** and **35** owner images.

Per decoded cell those spans are, in the owner image:

| Range | Read by |
|---|---|
| `NumBones`@240, `BoneIndex`@244 | the selected-bone loop, before it examines the mask |
| `numframes`@12, `animindex`@48 of the `StudioAnimDesc` | the same, and nothing else in the 72-byte descriptor |
| `weight`@0 of each selected bone's 32-byte record | both channel decoders, first, returning on zero |
| `offset[c]`@4+4c for the channels that decoder owns | position takes 0–2, quaternion 3–6 |
| `pos`@32, `quat`@44, `posscale`@60, `rotscale`@72, per channel | see `animation_and_movers.md` A.4 for which, when |
| two bytes per RLE run stepped over, plus the keys bracketing the frame | the walk stops at the frame; it does not cover the track |

Nothing else in the animation path is claimed. In particular the remaining 64 bytes of
each `StudioAnimDesc`, and the bulk of each 764-byte `StudioSeqDesc` beyond
`numblends`@52, `groupsize`@572, `paramindex`@580 and the fired grid cells, are read by
nobody this capture observed — which is recorded as unknown rather than as inert. Other
consumers do reach into that bulk: `flags`@8 and the transition fade triple at `+0x264`
are read outside the pose-sampling path, and are mapped below.

**`numframes`@12 is the format's only frame count, and `StudioSeqDesc` holds no second
copy.** A brute-force scan of all 764 bytes of `StudioSeqDesc` and all 72 bytes of
`StudioAnimDesc` on the `courtroom_bip1..7` models — every int in 4400–4800 and every
float in 145–160, the ranges that would hold that clip's 4,701-frame length or its
duration in seconds — returns `int@12 = 4701` and nothing else, bar one unrelated
bounding-box float on bip6. The controls behave identically: `ghoul_heather` 340,
`kueijin_part1_bip1` 3461, `snuff_bip1` 1331, `give_prince_key` 2021,
`prince_escort_male` 1801, `jack_vs_sabbat` 461 and `embrace_bips1` 1731 each reach a
single `StudioAnimDesc` through their sequence's base blend cell, with `numframes`@12 the
only count and `fps`@4 beside it. This is worth stating because the opposite is easy to
assume: a clip of that length is nonetheless one continuous authored animation rather than
a splice — on `courtroom_bip4.mdl` all **2,016** animated channels' RLE runs cover exactly
4,701 frames each, none truncated, run boundaries fall on multiples of 255 (the
run-length byte cap), and only 1 channel of the 2,016 starts a run at frame 4500.

### Which of those bytes an offline decoder does not read

Differencing the ranges above against the ranges `elysium_pipeline.formats.mdl_skel`
reads, measured by observing that decoder rather than by describing it: over the same
`sp_theatre` capture, **9,936 of 3,430,830** consumed bytes across all **34** owner
images are read by retail and by nothing offline. They are five fields:

| Field | Bytes | Owners | Read by retail for |
|---|---:|---:|---|
| `StudioAnimRecord.weight`@0 | 9,016 | 34 | the zero test that ends a bone's decode |
| `StudioSeqDesc.groupsize`@572 | 360 | 34 | the blend grid's axis extents |
| `StudioSeqDesc.paramindex`@580 | 360 | 34 | the pose parameter driving each axis |
| `StudioSeqDesc.numblends`@52 | 180 | 34 | how many cells the grid holds |
| `StudioSeqDesc.anim[16][16]`@56 | 20 | 2 | the fired cells beyond `[0][0]` |

The four sequence-descriptor figures are the same population reached by counting: the
run fires 45 distinct `(owner, sequence index)` identities, so 45×4, 45×8, 45×8; and the
20 grid bytes are ten 2-byte cells on the two `move_and_ranged` owners, which is the
blend-cell shortfall the source join measured as clips rather than as bytes.

**The weight is 1.0 wherever it is read.** All **2,254** decoded
`(owner, animation, bone)` triples in the capture carry `1.0`, so on this corpus the
absent read costs no output; what is absent is the zero test, and a record carrying zero
would decode as an ordinary one instead of the zero output retail writes.

The difference in the other direction is a property of the two walks rather than a
disagreement, and is measured at **7,993,786** bytes: an offline walk materialises a
whole RLE track where retail walks to the sampled frame (7,358,840 bytes), reads all 160
bytes of every bone where retail reads the bind and scale dwords a mask selected
(384,176), reads every sequence a model declares where a run fires a few dozen, and
follows the name strings no captured span claims. **35,858,024** bytes of the 34 images
are read by neither, and stay unknown.

None of the missing bytes fall in a loader-written range, so all of them are readable
from the installed file. Re-running the same decode against the installed image rather
than the captured one records the identical byte set on all 34 owners, which is what
says an offline read set is a property of the source rather than of the copy it was
handed.

**The `StudioBone.Flags` rewrite is purely additive.** Comparing all 2,286 captured bones
against their disk bytes, 627 across 27 models change — and every change *sets* bits that
were clear; **no bit is ever cleared**. The bits set are `0x4` (95 bones), `0x8` (600), and
`0x20`–`0x8000` (112–122 each), consistent with per-bone usage flags the loader computes
from hitboxes, attachments and vertex LODs. Their individual meanings are undecoded.

**`0x2` is never touched**: 27 bones carry it on disk and the same 27 carry it at runtime,
none disagreeing. So the split-inheritance rule
(`docs/vtmb/animation_and_movers.md` A.4a) reads a bit the loader leaves alone, and a disk
read of it is what the runtime uses. A decoder that reads `Flags` for any *other* bit is
reading a pre-load value.

**That region is not unreachable, and it is not a gap.** It is the include-model bone remap
array, one per include group, addressed by `StudioModelGroup`+0x10 *relative to the group
entry* — an index no header field points at directly, which is why a walk from the header
alone misses it. Measured over the 27 include-carrying models in one capture, holding the
runtime image against the installed file: the `+0x10` offset is byte-identical on disk in
**41 of 41** groups, so it is authored rather than loader-written; every one of the 41 array
bases lands inside the region; and the arrays span **173,320 of 173,320 bytes — 100.0% of
it**. An array holds one 56-byte record per bone of the *including* model. The 24,234 bytes
that differ from disk are the loader completing records it did not author whole, not a
separate structure.

The record layout is read from the consumer rather than from disk, and is owned by
`docs/vtmb/animation_and_movers.md` A.4b together with the remap rule that applies it.

(Header continues with flex/IK/mouth/pose/anim-block fields — irrelevant to static props;
the facial block starts at **344**, not the 336 a naive VAMPTools field walk gives, and is
mapped in `docs/vtmb/facial_animation.md`.)

**`+396` / `+400` are a count/index pair no public description of the format carries**, and
they address an array of 28-byte bone-chain dynamics records. The runtime consumes a first
moving bone, gravity, damping, a base-10 spring exponent and an angular limit; the one remaining
float at record +8 is not passed to the located client consumer. The shipped chains drive hair,
ponytails, manes and breasts. Modern Source has
`keyvalueindex`/`keyvaluesize` and `numlocalikautoplaylocks` at that offset, which is why a
decoder ported from the later format reads the bytes as a keyvalues offset and discards them.
`surfacepropindex` sits at `+392` and `NumIncludeModels` at `+404`, which brackets the pair
unambiguously. Layout, solver, render path, corpus and confidence ledger:
`docs/vtmb/secondary_motion.md`.

**`NumIncludeModels`@404 / `IncludeModelIndex`@408** reference external `.mdl`s
(the shared animation banks) via `StudioModelGroup[]`; static scenery props generally have
none, skeletal NPCs pull a recursive tree (`docs/vtmb/animation_and_movers.md` A.7). **`StudioModelGroup`
is 116 bytes** (`int FilenameIndex`@0 + `int LabelIndex`@4 + `int Filler[27]`, per VAMPTools);
`FilenameIndex` is **relative to the group-entry base** and yields a `models/`-rooted path.
Both offsets probe-verified (jeanette@404=1 → `shared/female/npc_allsequences.mdl`;
gangmember_male_2 the same). `elysium_pipeline.formats.mdl_skel.read_includes` reads them.

**`Filler` is not filler.** Most of it is disk padding the loader fills in, which is why the
rewrite table above lists three ranges inside these records. Read from the runtime image and
from the consumer that walks them (`docs/vtmb/animation_and_movers.md` A.4b):

| Off | On disk | At runtime |
|---|---|---|
| 0x04 | `0` | pointer to the loaded include model; its vtable slot `+0x4` returns that model's `studiohdr` |
| 0x08 | `0x7fffffff` sentinel | first virtual sequence index this group owns |
| 0x0c | `0` | how many virtual sequence indices it owns |
| 0x10 | authored offset | bone remap array, relative to the group entry (see above) |
| 0x14, 0x18 | `-1` | written by the loader; meaning undecoded |
| 0x44 | — | 24 `short` pose-parameter indices, remapping the caller's parameters into the include model's own |

A sequence index below `NumLocalSeq`@272 resolves against the model's own sequences;
otherwise the group whose `[0x08, 0x08+0x0c)` range contains it owns the sequence, and the
index becomes local to that owner.

### `mstudiobonecontroller_t` — 24 bytes, and never authored

`NumBoneControllers`@248 / `BoneControllerIndex`@252. The record is **24 bytes** (Source's is
56), with `type` at +4, `start`/`end` at +8/+12, and the **`inputfield` at +0x14** — the engine
looks a controller up by matching `inputfield` against the requested index, not by array
position.

**`NumBoneControllers` is 0 on all 4,255 `.mdl` in the retail VPKs and all 339 loose Unofficial
Patch models.** The lookup therefore returns null on every model in the game, and
`Studio_SetController` returns its input unchanged without writing anything. This is what makes
VtMB's NPC head turn inert: it is applied through bone controllers 0 and 1
(`docs/vtmb/facial_animation.md` → Gaze).

### `StudioSeqDesc` — fields outside the pose-sampling path

`NumLocalSeq`@272 / `LocalSeqIndex`@276, 764-byte stride. The descriptor's overall layout,
its blend grid, its activity key and **everything the engine does with the fields below**
are owned by `docs/vtmb/animation_and_movers.md` A.3; recorded here are the on-disk facts
for the fields the pose-sampling capture above does not reach.

**The transition fade triple — `+0x264` / `+0x268` / `+0x26c`.** Three floats carrying the
sequence's authored transition fade duration, in seconds, read by the client's transition
blender.

| Off | Type | Field | Note |
|---|---|---|---|
| 612 (`0x264`) | float | transition fade duration, seconds | |
| 616 (`0x268`) | float | the same duration | **byte-identical to `+0x264` in 100% of shipped content** |
| 620 (`0x26c`) | float | the same duration | likewise |

Because the three never differ, whatever cycle-dependent interpolation the engine performs
across them always collapses to one value per sequence. Across 331 loose models / 5,836
sequences the triple reads `(0.2, 0.2, 0.2)` ×5,762, `(0.3, 0.3, 0.3)` ×58 and
`(0.5, 0.5, 0.5)` ×16. The non-default clips are deliberate rather than noise: the 0.3 s
sequences are dialogue clips in `nines_damagedw.mdl`, `Jeanette.mdl`, `Therese.mdl` and
`Tourette.mdl`, and the 0.5 s ones are lying-down and damaged stance idles in
`hannah.mdl`, `heatherneardeath.mdl`, `lacroix.mdl` and `vv.mdl`.

**That survey is a large sample, not the whole corpus.** A capture of VPK-resident models
observes a fourth value, `0.45`, on the female `stances.mdl`, which the loose-model sweep
does not contain — so the four-value distribution above is a lower bound on the authored
vocabulary. Sweeping every VPK-resident `.mdl` for the triple is what would close it. How
the value is consumed is `animation_and_movers.md`.

**`flags`@8 — the corpus census.** Across the same 5,836 sequences the field takes exactly
five values, and nothing else occurs: `0x0002` ×2,642, `0x0000` ×2,217, `0x0001` ×815,
`0x0014` ×118, `0x0003` ×44. Notably `0x14` (`0x4 | 0x10`) is the additive family's whole
population — **118 sequences carry it, every one named `*_delta`, and all 118 `*_delta`-named
sequences carry exactly `0x14`, zero exceptions across the 331 models** — so the two bits
never separate on shipped content. What each bit *means* is `animation_and_movers.md`.

**Autolayers in the capture population — `numautolayers`@660 / `autolayerindex`@664.**
**461 of 2,478 captured sequence descriptors carry autolayers, and every one of them is in
`move_and_ranged.mdl`** (male or female), 0–2 entries per sequence: `smith_ready` →
`smith_aim_layer` (a 3×3 grid on the pose parameters `aim_yaw`/`aim_pitch`),
`baseballbat_aggressive_run` → `baseballbat_bobble_layer`, `smith_aggressive_run` →
`smith_aim_layer` + `smith_bobble_delta`. An entry is four bytes holding a bare sequence
index and carries no weight, no envelope and no flags, unlike modern Source's
`mstudioautolayer_t` — so the composition rule is **not derivable from the format**. It is read
out of the pose accumulator instead, and `animation_and_movers.md` owns it, along with the layer
weight that stays open and the install-wide census.

### `StudioModel` (**224B**, array at bodypart + `ModelIndex`)
`VertexData` is a 2-pointer runtime struct → **8 bytes** on x86; the following
offsets assume that. The **224-byte stride is measured**, off every multi-model bodypart in
the install (`mingxiao`, `cashbox`, `flashlight`, `jewelery_box`, `doorknob_round_brass`, …):
consecutive bodyparts' model arrays sit exactly `NumModels × 224` apart. 4,423 of the 4,444
models have one model per bodypart, so only a bodygroup's second and later models depend on
it (`mdl.py` still walks at 160 and is therefore correct for everything the prop path
touches). Details: `docs/vtmb/facial_animation.md`.

|---|---|---|---|
| 0 | char[64] | `Name` | |
| 64 | int | `Type` | |
| 68 | float | `BoundingRadius` | |
| 72 | int | `NumAttachments` | |
| 76 | int | `AttachmentIndex` | |
| 80 | int | *unidentified* | 0 on all 4,567 model records; **not** the eyeball pair |
| 84 | int | *unidentified* | |
| 88 | ptr[2] | `VertexData` | runtime; 8B reserved on disk |
| 96 | int[10] | `unused` | padding |
| 136 | int | `NumMeshes` | |

| 216 | int | `NumClothSpheres` | authored renderer-cloth collision spheres |
| 220 | int | `ClothSphereIndex` | **rel. to model base** → 20B records; ignore when count is zero |

`StudioRender`'s vertex accessor reads `pos = u16 · PositionScale + PositionOffset` from
these **per-model** fields rather than from the header hull; the two agree numerically on
every shipped model, so the hull-interpolation rule below is equivalent, but these are the
authoritative source.

The eyeball pair at 192/196 is fixed by its consumer: the eye pass resolves a record as
`model_base + *(int*)(model_base + 0xC4) + materialparam × 0x8C`. **301 models carry two
records each** — the whole character cast, players included. The record's layout and the
system it feeds are `docs/vtmb/facial_animation.md`.

The cloth fields are likewise fixed by StudioRender consumers rather than value shape. The +204
table selects particle/constraint definitions; +208/+212 and +216/+220 are transformed through
the current bone palette into capsule and sphere collision primitives before every cloth solve.
A zero primitive count can retain a nonzero offset, so count is the validity gate. The definition
record layout, solver and exact Jeanette/Sheriff payloads are `docs/vtmb/secondary_motion.md`.

`VertexData` here is `MeshVertexData` (1 ptr + int[8] = 36B).

| 32 | int | `MeshId` | runtime field; not needed by the offline geometry decode |
| 36 | float[3] | `Center` | runtime field; not needed by the offline geometry decode |
| 48 | int | `ClothSelectorIndex` | **rel. to mesh base** → `uint8[NumVertices]`; `0xFF` means ordinary skinning |
| 52 | int | `ClothPositionNormalIndex` | **rel. to mesh base** → `uint16[NumVertices]`; high bit reverses normal |
| 56 | int | `ClothTangentIndex` | **rel. to mesh base** → `uint16[NumVertices]` simulated tangent-output indices |

`materialtype`/`materialparam` are read by the hardware draw loop, which dispatches a
`materialtype == 1` mesh to the eye path and every other mesh to the ordinary one. **598 meshes
across 299 models are flagged**, always in pairs with `materialparam` 0 and 1
(`docs/vtmb/facial_animation.md`).

The final three fields are authored only for renderer cloth. All three are nonzero together on
**84 of 9,741** installed mesh records and never appear partially. Generated StudioRender vertex
routines read the selector first: `0xFF` preserves the ordinary skinned vertex; any in-range cloth
definition selects simulated position/normal/tangent output through +52/+56. Those maps are a
post-skin substitution, so the presence of valid biped weights on the same vertices does not imply
the surface is rigid. Carrier census and runtime behavior are `docs/vtmb/secondary_motion.md`.

### Embedded vertices — three formats keyed by `StudioModel.VertexListType`

Array at `model + VertexIndex`; mesh *m*, mesh-local id *i* → global index
`Mesh.VertexOffset + i`. **Scenery distribution (3,330 `models/scenery/**` .mdl):
SKINNED 60% / UNSKINNED 31% / COMPRESSED 9%** — all three are needed. Empirical
stride confirmed by `(TangentsIndex − VertexIndex) / NumVertices`. All three
**probe-validated** (positions land in `[HullMin,HullMax]`, UVs clean):

**`VertexListType == 0` — SKINNED `StudioVertex` (44B, exact).** Natural C++
alignment pads `BoneWeight` to 12B (not the packed 42 the header comment implies):
| Off | Type | Field |
|---|---|---|
| 0 | byte[3] | `BoneWeight.Weight` |
| 4 | short[3] | `BoneWeight.Bone` (2-byte aligned, pad @3) |
| 10 | byte | `BoneWeight.NumBones` |
| 12 | float[3] | `VecPosition` (real Source coords) |
| 24 | float[3] | `VecNormal` |
| 36 | float[2] | `VecTexCoord` (u,v) |

Both packed forms share one shape — quantized position, **one** packed-normal
slot, then **u16 u, u16 v** — settled by an install-wide sweep (all 1,082
UNSKINNED + 361 COMPRESSED models): the normal slot is bit-identical across all
three corners on ~35% of triangles (flat faces share a normal; real UVs never
do), and reading it as U collapses 100% of some models' UV triangles to zero
area — texture smeared into vertical streaks. With the layouts below, no model
is degenerate and the 3D→UV mapping is near-conformal (median log₁₀ singular
-value ratio 0.22, vs 0.85+ for every other channel pairing).

**`VertexListType == 1` — UNSKINNED `StudioVertex2` (12B, 6× u16).** Positions are
hull-normalized; **decode = `HullMin + (u16/65535)·(HullMax−HullMin)`** per axis
(VAMPTools' `·HullMin`-only form is wrong):
| Off | Type | Field |
|---|---|---|
| 0 | u16[3] | position scalars (x,y,z) → hull-interpolate |
| 6 | u16 | packed normal (unused; regenerate from geometry) |
| 8 | u16[2] | `VecTexCoord` (u,v) = raw/65535 |

**`VertexListType == 2` — COMPRESSED `StudioVertex3` (8B).** Byte-quantized
position, full-precision UVs:
| Off | Type | Field |
|---|---|---|
| 0 | byte[3] | position scalars → `HullMin + (b/255)·(HullMax−HullMin)` |
| 3 | byte | packed normal (unused; regenerate from geometry) |
| 4 | u16[2] | `VecTexCoord` (u,v) = raw/65535 |

The packed-normal slot is **exact, not unreliable** — it indexes a table compiled into
`StudioRender.dll`, not the model: UNSKINNED's u16 is a *byte offset* into the 5,314-entry
unit-vector table at `0x2C06E008`, COMPRESSED's byte is an index into a second table at
`0x2C06D358` with stride 16. Decoding either needs the user's own DLL, so the prop path
regenerates normals from geometry instead (as the world path does via `SurfaceTool`); the
facial pipeline, which has no geometry to regenerate from, reads the table
(`docs/vtmb/facial_animation.md` → "The unit-vector table", `research/tooling/probes/probe_facial.py --anorms`).

### Skin table — `short skinref[NumSkinFamilies][NumSkinRefs]` at `SkinIndex`

`skinTable[family][skinref]` → texture index. A mesh's `StudioMesh.Material` is a **skinref**;
the family row remaps it, which is how one model draws several skins — a traffic light's
red/walk/flashing/yellow, a doorknob's locked/unlocked, a laser emitter's armed/idle. The entity
picks the row with its `skin` keyfield/input (`m_nSkin`).

**Family 0 is the identity row on all 4,445 readable models in the install**, so reading
`StudioMesh.Material` as a texture index yields the correct skin-0 material — and nothing else.
201 models carry more than one family; 12 have an absent or unreadable table (treat as a single
identity family). `pipeline/src/elysium_pipeline/formats/mdl.py::skin_table` / `skin_families` decode it, and
`write_obj_scene` emits `props/<stem>.skins` for any model with alternate families.

Worked example — `models/scenery/street/StreetLight/StreetLight.mdl`, 15 textures / 9 skinrefs /
5 families:

| family | pedlight | lightred | lightyellow | lightgreen | state |
|---|---|---|---|---|---|
| 0 | `pedlight_stop` | `lightred_on` | `lightyellow` | `lightgreen` | red |
| 1 | `pedlight_Walk` | `lightred_OFF` | `lightyellow` | `lightgreen_ON` | green + walk |
| 2 | `pedlight_Flash` | `lightred_OFF` | `lightyellow` | `lightgreen_ON` | green + flashing |
| 3 | `pedlight_stop` | `lightred_OFF` | `lightyellow_ON` | `lightgreen` | amber |
| 4 | `pedlight_flash002` | `lightred_OFF` | `lightyellow` | `lightgreen` | all off + flashing |

The swap carries emission with it: `lightred_on` has a `$selfillum` mask, `lightred_OFF`
(basetexture `lightred`) has none — so the lamp's glow goes out with its colour.

### `StudioTexture` (material) — array at `TextureIndex`
| Off | Type | Field | Note |
|---|---|---|---|
| 0 | int | `NameIndex` | **rel. to the StudioTexture base** → material name string |
| 4 | int | `Flags` | |
| 8 | int | `Used` | |
| 12 | ptr | `material` | runtime (4B x86) |
| 16 | ptr | `clientmaterial` | runtime (4B x86) |

On-disk stride is smaller than modern Source's 64B (VtMB drops `unused[10]`); **probe
the stride** (candidates 20/24/64) by checking each `NameIndex` yields sane ASCII.
The name is a **material name** (e.g. `chinabldg04`), resolved to a `.vmt` via the
search paths — feeds straight into our existing VMT + TTH/TTZ resolver + PAKFILE.

Texture **search paths**: `NumTextureSearchPaths` ints at `TextureSearchPathIndex`;
each int is a header-relative offset to a path string (e.g. `models/scenery/…/`).

## `.dx80.vtx` — `OptimizedModel` (`#pragma pack(1)`, exact offsets)

Parallel tree to the `.mdl`; you walk both in lockstep. All `*Offset` fields are
**relative to the struct that owns them**.

### `FileHeader_t` (36B @0)
| Off | Type | Field |
|---|---|---|
| 0 | int | `version` (== **107** in VtMB, not the stock 7) |
| 4 | int | `vertCacheSize` |
| 8 | u16 | `maxBonesPerStrip` |
| 10 | u16 | `maxBonesPerTri` |
| 12 | int | `maxBonesPerVert` |
| 16 | int | `checkSum` (matches `.mdl`) |
| 20 | int | `numLODs` |
| 24 | int | `materialReplacementListOffset` |
| 28 | int | `numBodyParts` |
| 32 | int | `bodyPartOffset` |

### Nesting (all offsets relative to the owning header)
- `BodyPartHeader_t` (8B): `numModels`@0, `modelOffset`@4 → `ModelHeader_t[]`
- `ModelHeader_t` (8B): `numLODs`@0, `lodOffset`@4 → `ModelLODHeader_t[]`
- `ModelLODHeader_t` (12B): `numMeshes`@0, `meshOffset`@4, `switchPoint`@8 → `MeshHeader_t[]`
- `MeshHeader_t` (8B): `numStripGroups`@0 (u16), `stripGroupHeaderOffset`@4 → `StripGroupHeader_t[]`
- `StripGroupHeader_t` (**20B** — VtMB's compact form, probe-confirmed): `numVerts`@0 (u16),
  `numStrips`@4 (u16), `vertTableOffset`@8, `indexOffset`@12, `stripOffset`@16
- `StripHeader_t` (16B): `numIndices`@0 (u16), `indexOffset`@2 (u16), `numVerts`@4 (u16),
  `vertOffset`@6 (u16), `flags`@8 (byte), `spacing[7]`@9

**Vertex table**: array at `stripgroup + vertTableOffset`, one entry per
`StripGroupHeader_t.numVerts`, each yielding a **mesh-local vertex ID**. VtMB writes
it in **two forms**, and **no header field distinguishes them**:

| Form | Stride | ID | Used by |
|---|---|---|---|
| flat | 2B | `u16` @0 | retail's static props |
| record | 12B | `u16` @**10** (bone data @0–9, `0xffff` @8) | every non-static model, plus the patch's 22 recompiled static models |

`STUDIOHDR_FLAGS_STATIC_PROP` does **not** predict the form: across the install's
4,425 models every flat model is static (3,278/3,278), but 22 static models are the
record form — all of them loose Unofficial Patch files (`vw_bus`, `paneltruck/truck`,
the `lightningbird`/`limo`/`yugo`/`copcar` vehicles, `libcolumn_*`, `projector`, …),
recompiled by the patch team with a tool that emits bone records regardless.

**Detect per stripgroup** (`mdl._vtable_form`): a stripgroup's table maps its entries
to *distinct* mesh vertices, so read it both ways and take the form whose IDs are all
distinct and `< StudioMesh.NumVertices`. The wrong form reads bone bytes as IDs and
collides or overshoots. This is unambiguous in practice: over all 819 stripgroups of
the 548 models our maps place, exactly one form ever qualifies — never two, never
zero. (Reading the flat form on a record-form model sends offsets past EOF: that is
the `unpack_from requires a buffer of at least …` failure.)

The ~405 models neither form fits are the skeletal `character/**` NPCs, which the prop
pipeline does not decode; `decode` raises on them rather than emitting garbage.
**Index table**: array of u16 at `stripgroup + indexOffset` — each indexes the vertex table.

## The walk (LOD0 only) — from `Mesh.cpp`

```
for bp in range(header.NumBodyParts):                 # mdl & vtx in lockstep
  mdl_part, vtx_part = mdl.bodypart(bp), vtx.bodypart(bp)
  for m in range(mdl_part.NumModels):
    model, vtx_model = mdl_part.model(m), vtx_part.model(m)
    vtx_lod = vtx_model.lod(0)                         # LOD0
    for mi in range(model.NumMeshes):
      mesh     = model.mesh(mi)                        # StudioMesh
      vtx_mesh = vtx_lod.mesh(mi)                      # MeshHeader_t
      material_name = texture(mesh.Material).name      # → .vmt → basetexture
      for sg in vtx_mesh.stripgroups:
        stride, off = detect_vtable_form(sg)           # (2,0) flat or (12,10) record
        vtable = bytes at sg.vertTableOffset
        itable = u16[] at sg.indexOffset
        for strip in sg.strips:
          for k in range(0, strip.numIndices, 3):      # tri list
            a,b,c = itable[strip.indexOffset + k + 0..2]
            for local_id in (a,b,c):
              mesh_vert_id = u16 at vtable + local_id*stride + off
              global_id    = mesh.VertexOffset + mesh_vert_id
              v = StudioVertex at model + model.VertexIndex + global_id*44   # SKINNED stride
              # v.VecPosition, v.VecNormal, v.VecTexCoord
```

Notes:
- **Winding:** VAMPTools emits `(a,c,b)` (reversed) for FBX; the world path is
  `cull_disabled`, so winding only affects normals/backfaces there.
- **UV V:** VAMPTools flips to `1 - v` for FBX; our world exporter uses UVs as-is
  (Source convention).
- **Coordinates:** `pipeline/src/elysium_pipeline/formats/mdl_gltf.py` is the settled exporter for props — it emits
  standard glTF 2.0, which is self-describing, so glTFRuntime reorients it into
  Unreal space at load with no manual `source_to_unreal` conversion needed (the one
  exemption to the `UE_` exporter convention; see `pipeline/CLAUDE.md`). The `sprp`
  per-instance origin/angles/scale still apply on top when placing the prop.

## Materials → our existing pipeline

`StudioTexture.name` (+ search paths) → `<name>.vmt` → `$basetexture` →
`<basetexture>.tth`/`.ttz`. Every step exists: `pipeline/src/elysium_pipeline/formats/vmt.py`,
`pipeline/src/elysium_pipeline/formats/tex_to_png.py`, PAKFILE resolution in `pipeline/src/elysium_pipeline/formats/bsp.py`. Model material resolution
reuses the world resolver verbatim.
