Read-only walk of the six retail functions of story `L0.entity_core.data-object-registry` (brief `-1`): 0x1003cbc0, 0x1003cb00, 0x1003cd50, 0x1003cf50, 0x1003cc80, 0x1003d130. Re-read and corrected by the confirming reader; the verdict per function and the list of corrections are in `## Confirmation`.

Sources: `vtmb_code` and `vtmb_asm` for every function (asm is the authority for constants, call order, return register and stack balance; the decompile's `byte` parameters and `this_00[4].field_0x444`-style indexing are artifacts, see Shared inputs); `vtmb_callers`, `vtmb_globals`, `vtmb_grep`, `vtmb_fields`, `vtmb_vtable`, `vtmb_func`; `uv run elysium research where` per address. `research where` lists no `docs/vtmb` section for these addresses, so `research section` was not run.

## Corrections to the brief

- The port has no data-object code. `research where` cites none of the six. The only port reference is the layout row `Private/Substrate/ElysiumNpcKernelShape.cpp:279` (`CAI_BaseNPCTroika`, `0x0444 m_fDataObjectTypes`). There is no mask member, no registry and no accessor in `Source/`.
- The registry is not filled by runtime registration. Four retail accessors are written once, at system init (`CDataObjectAccessSystem::Init`, 0x1003c660). Nothing else in vampire.dll writes it.
- Every external call site passes type 1. The only non-literal index is the loop in `DestroyAllDataObjects` (1003d300), over 0–3, with no vampire.dll caller. So in the decompiled corpus only bit 1 is ever set, and the accessors registered for types 0, 2 and 3 are never reached by any decompiled path.
- The mask uses `type & 31` in all six. The dispatch range check is on the signed type. Types 32, 33 and −1 therefore alias to bits 0, 1 and 31 for every mask write.
- The brief's invalid-type probe cannot be driven through a retail entry (see Record notes).
