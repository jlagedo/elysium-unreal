# Lanes Q1–Q4 · the inline cells (wave 4; four lanes, disjoint by file)

Read `README.md` first. Your lane number is in your prompt; you own exactly the files listed in
`cells-Q<n>.txt` in this directory (all under `Source/ElysiumUE/Private/Substrate/`), plus the
tests that pin the values you move. You may not edit the tunables overlay
`research/tooling/ghidra/driver/kernel_tunables.tsv` or the generated
`ElysiumNpcKernelTunables.h/.cpp`: you deliver rows, the orchestrator applies and regenerates.

## Why

Story 4 (0019/4) made `kernel_tunables.tsv` the one home for every retail constant the kernel
reads: a row is `address  name  type  value  evidence`, `gen_kernel_tunables --check` re-reads
each row out of the pinned `vampire.dll` at its width, and the port reads
`ElysiumNpcTunables::<Name>` (`ElysiumNpcKernelTunables.h`), never a literal. Row 05 left a
queue: `gen_kernel_tunables --report` counts every `DAT_1xxxxxxx` spelled in
`Substrate/ElysiumNpc*` that the overlay does not hold (`kernel_ledger.inline_cells`), comments
included. It stands at 408 mentions over 215 files. This story executes the whole queue.

## What a mention is, and what you do with it

Find yours with `rg -n "DAT_10[0-9a-f]{6}" <your files>`. Each mention is one of:

1. **A constant the port reads** — a literal in code (or a `constexpr` next to it) with the
   `DAT_` address in a comment beside it: `if (Dist > 180.0f)   // _DAT_1044c3a8`. Move it: add a
   row to `cells-Q<n>.tsv` (`address<TAB>Name<TAB>type<TAB>value<TAB>evidence<TAB>file:line`),
   with `type` one of `f32`, `f64`, `i32`, `u32` (a pooled cell) or `imm_f32` / `imm_i32` (an
   immediate in the instruction stream: the address is then the instruction's), the evidence
   naming the reader function and what the value is for. Replace the literal in code with
   `ElysiumNpcTunables::<Name>` — the header is regenerated by the orchestrator, so pick the
   name now and use it; the build joins them. **Reuse an existing name** when the overlay already
   holds the same address (`rg <address> kernel_tunables.tsv`); the report only counts
   addresses it does not hold, so a duplicate means you mis-read the address. Where the same
   address is read at several sites, one row, every site.
2. **A retail global that is not a value** — an engine pointer (`gpGlobals`, `Time()` vtables),
   a table base, a ConVar object, a class static, a string pointer — spelled in a comment or as
   the name of a seam word. That is not a tunable. Record it in `refs-Q<n>.tsv`
   (`address<TAB>Name<TAB>what it is<TAB>file:line`); the orchestrator gives the overlay a `ref`
   row type so the ledger names it and the meter stops counting it. Do not reword the comment
   to hide the address.
3. **A ConVar** read through its pointer at object+4: covered by the object's `convar_*` row;
   if the overlay lacks the object, add a `convar_f32` / `convar_i32` row for the OBJECT address
   with the ConVar's name and shipped default (read from the image's static initialiser, the
   same way `gen_kernel_tunables` checks them; story 4's rows are the pattern).
4. **A mention inside a `dead` body that survived** — should not exist after waves 1 and 3; if
   you find one, report it (address, file:line) under "Needs another owner" and leave it.

Rules: retail's value, retail's width, no rounding (the generator's `--check` reads the image
and Errors with both numbers on a mismatch); a `float` read as `double` in retail is `f64` at
retail's width even when the port stores it in a float. Names follow the overlay's style
(`WerewolfStuckHullScale`, `AngleQuantum`): what it is, not where. Tests that pin a literal keep
pinning it through the accessor.

## Deliver

`report-Q<n>.md` (≤200 words): counts per kind (moved / ref / convar / left), the files with
the most, anything odd. `cells-Q<n>.tsv` and `refs-Q<n>.tsv` beside it. Finish with
`rg -c "DAT_10[0-9a-f]{6}"` over your files showing zero mentions outside those in `refs-Q<n>.tsv`
(a ref stays spelled; the overlay row absorbs it).
