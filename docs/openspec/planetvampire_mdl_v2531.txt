[font size="6"][b]VtMB MDL v2531[/b][/font]

[font size="5"][b]What Bloodlines stores, how the retail game evaluates it, how it differs from later Source, and what existing tools recover[/b][/font]

Vampire: The Masquerade — Bloodlines identifies its [font face="courier new"]IDST[/font] models as version [b]2531[/b]. The family resemblance to later Source is real, but copying modern structures reads fields at the wrong offsets, skips deformation systems, or exports a pose the retail game never draws.

Settled facts, tool approximations, and remaining unknowns are kept separate. No game-derived files are redistributed here.

[hr]

[font size="5"][b]1. Four questions that are not the same accomplishment[/b][/font]

[ol type="1"][li][b]Parsing[/b] — structures, strides, counts, offsets, sibling files.[/li][li][b]Extracting[/b] — geometry, skeleton, bind, materials, sequences, channels, flexes, metadata.[/li][li][b]Reproducing retail[/b] — selection, blending, hierarchy, procedural, secondary motion, face, and render in the same order.[/li][li][b]Authoring[/b] — a file [font face="courier new"]vampire.exe[/font] will load and play.[/li][/ol]

A correct static mesh proves neither animation decode nor pose equivalence. A donor animation patcher proves real write-back, not a general compiler.

[hr]

[font size="5"][b]2. The format in one screen[/b][/font]

A model is:

[ul type="disc"][li]an [font face="courier new"]IDST[/font] 2531 [font face="courier new"].mdl[/font] — header, bones, sequences, channels, materials, embedded vertices, flex, eyes, Troika extensions;[/li][li]a sibling [font face="courier new"].dx80.vtx[/font] and/or [font face="courier new"].dx7_2bone.vtx[/font] — strip/index topology;[/li][li]an optional [font face="courier new"].phy[/font] — VPhysics;[/li][li][font face="courier new"].vmt[/font] materials and [font face="courier new"].tth[/font]/[font face="courier new"].ttz[/font] textures;[/li][li]other [font face="courier new"].mdl[/font] files included as shared animation libraries.[/li][/ul]

[quote][b]There is no [font face="courier new"].vvd[/font]. Vertices live inside the [font face="courier new"].mdl[/font].[/b][/quote]

[quote][b]Animation is a fixed 32-byte record per bone and seven classic RLE channels, not later Source's linked [font face="courier new"]mstudioanim_t[/font].[/b][/quote]

[quote][b]The drawn pose is not the decoded clip. Retail adds selection, grids, masks, additive layers, transitions, include remapping, split inheritance, AxisInterp, a persistent partial bone palette, and secondary motion.[/b][/quote]

[quote][b]A held weapon is a second studio model. Matching bones copy the wearer's world matrices; unmatched bones keep the weapon's own clip. It is not parented to a [font face="courier new"]StudioAttachment[/font].[/b][/quote]

[quote][b]A skinned vertex authors up to four influences. The fourth weight is [font face="courier new"]255 - sum[/font] of the three stored bytes. The DX8 hardware path then drops that fourth influence; the software path and [font face="courier new"].dx7_2bone.vtx[/font] keep it.[/b][/quote]

[b]On disk.[/b] Header-level indexes are from the header base; nested structures use owner-relative or record-relative offsets. Count is the validity gate: an empty array's index often points at the next write cursor. The unused transition index collides with the bodypart index, and the unused bone-controller index collides with the attachment index, on every shipped model. Those equalities do not mean attachments are empty.

Some images end with a ten-byte compiler trailer inside the declared length: a [font face="courier new"]uint32[/font] path offset plus magic [font face="courier new"]QnDbTm[/font]. The engine does not read it. Unindexed include groups, donor animation payloads, and duplicate AxisInterp tables are the same class: compiler-retained cache. Walk the declared counts.

[b]At runtime.[/b] The loader maps the file and patches it in place. Activity IDs, include ranges, init flags, and bone-usage flags may have been rewritten. A memory dump is not the file.

[font size="4"][b]3.2 [font face="courier new"].vtx[/font] — version 107[/b][/font]

Topology is [font face="courier new"].dx80.vtx[/font] and/or [font face="courier new"].dx7_2bone.vtx[/font], never [font face="courier new"].dx90.vtx[/font]. [font face="courier new"]fish07_school.mdl[/font] ships only DX7. Variants need only agree on overlapping LODs (Barabus: identical LOD0, extra LODs in DX7).

Walk in lockstep with the [font face="courier new"].mdl[/font]: [font face="courier new"]bodypart → model → LOD → mesh → stripgroup → strip → index[/font]. Nested offsets are owner-relative.

The stripgroup is 20 bytes. Flags at [font face="courier new"]+6[/font] select the vertex table:

[ul type="disc"][li][font face="courier new"]0x10[/font] — flat 2-byte mesh-local ID (most static props);[/li][li][font face="courier new"]0x08[/font] — 12-byte record, ID at byte 10 (characters, and some recompiled statics).[/li][/ul]

Refuse a stripgroup that sets neither. [font face="courier new"]STUDIOHDR_FLAGS_STATIC_PROP[/font] is not a substitute.

12-byte record:

[table][tbody]
[tr][td style="padding:3px;"]0[/td][td style="padding:3px;"][font face="courier new"]u16 boneWeightIndex[/font] — row of a 65-row permutation table[/td][/tr]
[tr][td style="padding:3px;"]2,4,6,8[/td][td style="padding:3px;"]four [font face="courier new"]s16[/font] hardware palette slots; [font face="courier new"]0xffff[/font] unused[/td][/tr]
[tr][td style="padding:3px;"]10[/td][td style="padding:3px;"][font face="courier new"]u16 origMeshVertID[/font][/td][/tr]
[/tbody][/table]

Observed flag values: [font face="courier new"]0x09[/font] FLEXED+record, [font face="courier new"]0x0a[/font] HWSKINNED+record, [font face="courier new"]0x0b[/font] both, [font face="courier new"]0x0c[/font] flat. [font face="courier new"]StripHeader_t[/font] carries index/vertex counts, a bone count, and a [font face="courier new"]{hardwareID, newBoneID}[/font] table. On character models that palette is ordinary [font face="courier new"].mdl[/font] bone order.

16-bit indices into the vertex table, plus [font face="courier new"]StudioMesh.VertexOffset[/font], address the embedded vertex array.

[font size="4"][b]3.3 [font face="courier new"].phy[/font][/b][/font]

Optional VPhysics: 16-byte [font face="courier new"]phyheader_t[/font] (size, id, solid count, checksum), then one legacy IVP solid per count, then a KeyValues tail. No [font face="courier new"]VPHY[/font] magic; [font face="courier new"]IVPS[/font] sits at solid [font face="courier new"]+0x2C[/font] and is zeroed on some otherwise ordinary files. [font face="courier new"]VCollideLoad[/font] receives the bytes after the 16-byte header, so the checksum never reaches the loader.

Hair, breasts, ponytails, skirts, and coats are not this file. See §14.

[font size="4"][b]3.4 Materials[/b][/font]

[font face="courier new"]StudioMesh.Material[/font] is a skin reference:

[font face="courier new"]skinTable[family][meshSkinRef] → StudioTexture index[/font]

Family 0 is identity in shipped content. Alternate families are authored states (signals, locked/unlocked, illum).

[font face="courier new"]StudioTexture[/font] is 20 bytes and names a [font face="courier new"].vmt[/font], not an image. [font face="courier new"]Flags[/font]/[font face="courier new"]Width[/font]/[font face="courier new"]Height[/font] are unused zeros. [font face="courier new"]+16[/font] is the compiler's max world-units-per-texel metric; StudioRender reads the name only.

[font size="5"][b]4. Geometry[/b][/font]

[ul type="disc"][li][font face="courier new"]StudioBodyPart[/font] — 16 bytes.[/li][li][font face="courier new"]StudioModel[/font] — [b]224 bytes[/b]. Most bodyparts have one model, so a shorter stride appears to work until the second model of a bodygroup.[/li][li][font face="courier new"]StudioMesh[/font] — 60 bytes, including eye and cloth fields. Cloth maps at [font face="courier new"]+48/+52/+56[/font] are LOD-major (§14.2).[/li][/ul]

[font face="courier new"]StudioModel.Name[/font] is [font face="courier new"]char[128][/font], same widening as the header. Three wield records run past 64 characters ([font face="courier new"]w_{m,f}_flamethrower[/font], [font face="courier new"]w_f_sledgehammer[/font]); a 64-byte overlay then reads name text as type/radius. [font face="courier new"]Type[/font] and [font face="courier new"]BoundingRadius[/font] at 128/132, and the reserved pair at 184, are zero.

The cloth definition table at [font face="courier new"]+204[/font] is LOD-major: extent is [font face="courier new"]NumVertices × VTX numLODs[/font], not the definition row count.

[font size="4"][b]4.1 Three vertex formats[/b][/font]

[font face="courier new"]StudioModel.VertexListType[/font] selects one of three embeddings. All three occur in scenery.

[b]Type 0 — skinned, 44 bytes[/b]

[table][tbody]
[tr][td style="padding:3px;"]0[/td][td style="padding:3px;"]three byte weights; fourth weight = [font face="courier new"]255 - sum[/font][/td][/tr]
[tr][td style="padding:3px;"]3[/td][td style="padding:3px;"]selector; count = [font face="courier new"]max(1, selector % 5)[/font][/td][/tr]
[tr][td style="padding:3px;"]4[/td][td style="padding:3px;"]four [font face="courier new"]s16[/font] bone indices[/td][/tr]
[tr][td style="padding:3px;"]12 / 24 / 36[/td][td style="padding:3px;"]float position / normal / UV[/td][/tr]
[/tbody][/table]

There is no count byte. The byte a three-influence overlay reads as a count is the low half of [font face="courier new"]Bone[3][/font], zero whenever the fourth slot is unused.

Knox's collar and manbat use the fourth slot. Retail then:

[ul type="disc"][li]software — blends up to four matrices from the vertex;[/li][li]DX8 hardware — materialises weights from the VTX, permutes, writes [font face="courier new"]numUsed[/font] renormalised; shipped [font face="courier new"].dx80.vtx[/font] never keeps four;[/li][li][font face="courier new"].dx7_2bone.vtx[/font] — keeps all four.[/li][/ul]

A native reader should keep what was painted. The three-influence DX8 result is a hardware budget, not authoring.

[b]Type 1 — unskinned, 12 bytes[/b] — three [font face="courier new"]u16[/font] position scalars, [font face="courier new"]u16[/font] packed-normal offset, two [font face="courier new"]u16[/font] UV scalars. [font face="courier new"]position = PositionOffset + uint16 * PositionScale[/font]. Those fields agree with interpolation through the hull; multiplying only by the minimum bound does not.

[b]Type 2 — compressed, 8 bytes[/b] — three byte position scalars, byte packed-normal index, two [font face="courier new"]u16[/font] UV scalars.

[font size="4"][b]4.2 Normals and winding[/b][/font]

Every format carries a normal. Packed formats address renderer unit-vector tables, which also serve compressed facial deltas. Co-located split vertices often hold different authored normals (nostrils, sockets, hard edges). Do not recompute from triangles.

VAMPTools reverses winding and flips V for FBX. That is an export conversion, not a v2531 rule.

Skinning is current bone-to-world times [font face="courier new"]poseToBone[/font]. A valid rest mesh only shows that these cancel at bind.

Seven shipped models (including [font face="courier new"]ash[/font], [font face="courier new"]brian[/font]) have more than one parentless bone. Reparent extras onto the principal root if the host requires one root. Do not splice a synthetic bone 0: shared-bank clips assume [font face="courier new"]Bip01[/font] sits there.

[font size="4"][b]5.2 Attachments and hitboxes[/b][/font]

[font face="courier new"]StudioAttachment[/font] is 60 bytes: record-relative name, unread flags, bone, row-major 3×4 (last column = Source-inch translation). It is an effect origin ([font face="courier new"]mouth[/font], [font face="courier new"]eyes[/font], [font face="courier new"]muzzleflash[/font], melee [font face="courier new"]slampoint[/font]). [font face="courier new"]LookupAttachment[/font] is 1-based (0 = not found) and walks includes.

It is not how wielded geometry is parented (§16.2). Wield models do declare attachments — some firearms have three-slot tables — but they carry zero animation events, so positional muzzle/brass/clip slots never fire. The only by-name lookup on a held weapon asks for [font face="courier new"]muzzleflash[/font]. [font face="courier new"]w_m_bushhook[/font] has a [font face="courier new"]slampoint[/font]; [font face="courier new"]w_f_bushhook[/font] has none.

Hitbox sets are 12 bytes (record-relative name, count, record-relative box index). Each box is 32 bytes: bone, group, bone-local min/max. The name is not file-absolute; on LaCroix the absolute reading lands in a flex payload.

[font size="4"][b]5.3 Bone controllers and IK[/b][/font]

The controller record is 24 bytes. Every shipped model declares zero, so the NPC head-controller writes to indices 0 and 1 are inert. Visible head turns come from animation and choreography.

IK chains are authored (typically four hand/foot chains of three 28-byte links; [font face="courier new"]KneeDir[/font] is always zero) and unused. [font face="courier new"]numikrules[/font] is 0, there is no lock pair, and no shipped module solves them. They are leftovers, not a missing stage.

[font size="5"][b]6. Animation records[/b][/font]

[font face="courier new"]StudioAnimDesc[/font] is 72 bytes: name, FPS, flags, frame count, movement, bounds, offset to bone data.

At [font face="courier new"]animdesc + animindex[/font], one 32-byte record per bone, header order:

[code]
float weight;   // binary ownership mask
int offset[7];  // pos X/Y/Z, quaternion X/Y/Z/W
[/code]

A non-zero offset is relative to that record and addresses [font face="courier new"]{valid,total}[/font] RLE of [font face="courier new"]int16[/font]. Zero means the channel is absent.

[code]
union { struct { uint8 valid, total; }; int16 value; };
[/code]

The first [font face="courier new"]valid[/font] frames are explicit; [font face="courier new"]valid[/font] through [font face="courier new"]total-1[/font] hold the last value. Retail walks only to the requested sample. An offline decoder must still bound every step against the image.

[font size="4"][b]6.1 Position adds; rotation replaces[/b][/font]

[code]
position:   present ? bind + sample * posscale : bind
quaternion: present ? sample * rotscale        : bind component
then normalize
[/code]

Missing rotation components keep bind; they are not zero. A clavicle that animates only W becomes ~150° off if X/Y/Z are zero-filled. Adding bind to the animated components double-counts bind.

[font size="4"][b]6.2 [font face="courier new"]weight[/font] is ownership, not a blend[/b][/font]

The field is [font face="courier new"]0.0[/font] or [font face="courier new"]1.0[/font]. Retail tests it before tracks. Zero means “this layer does not own this bone,” which is not the same as an owned bone with no channels (that one holds bind). Head-only and arm-only layers need the distinction.

On shared locomotion banks the mask follows grip. Two-handed clips (every firearm, plus bush hook and sledgehammer) keep a 49-bone upper-body set including [font face="courier new"]Bip01 Spine1[/font] and the seven prop bones in §16.2. One-handed melee keeps a 24-bone right-arm set. Every cell of a shipped blend grid carries the same mask.

[font size="5"][b]7. Sequences[/b][/font]

[font size="4"][b]7.1 Timing[/b][/font]

FPS is per animation descriptor (18, 20, 30, and 60 occur).

[code]
x = (numframes - 1) * cycle
frame = floor(x)
fraction = x - frame
duration = (numframes - 1) / fps
[/code]

Between keys, rotation is a hemisphere-aligned component lerp then normalize, not a slerp. Position is a plain lerp on the same fraction. The last authored sample is at cycle 1.0.

Seven one-sequence scenery/prop models run an autolayer count into their string table and zero the melee block. Bound counts against the image. A non-finite reach on those files is unstated, not a swing of range zero.

The cell is [font face="courier new"]anim[i0][i1][/font], axis 0 at stride 16. A transpose agrees on a 9×1 walk fan and fails on a 3×3 aim grid. Authored grids are a subrectangle of the physical 16×16 (9×1, 3×3, 2×1, 5×1).

[font size="4"][b]7.3 Pose parameters and selection[/b][/font]

20-byte descriptor: record-relative name, flags, start, end, loop modulus. Vocabulary: [font face="courier new"]move_yaw[/font] and [font face="courier new"]hit_yaw[/font] ([font face="courier new"]-180..180[/font], loop 360); [font face="courier new"]aim_yaw[/font]/[font face="courier new"]aim_pitch[/font] on player aim models.

Wrap, normalize through the descriptor range, remap through the sequence range, clamp, return adjacent cells plus a fraction. Interpolate by normalized cycle; cells may differ in FPS and length. The 9×1 [font face="courier new"]move_yaw[/font] fan is backpedal at both ends, forward in the centre.

Player [font face="courier new"]move_yaw[/font] is right-positive from realized velocity, slewed while movement is fresh, held while still. Aim yaw is left-positive and aim pitch down-positive. Ordinary player selection writes aim yaw as 0, so the 3×3 weapon grid is a pitch blend in the centre column.

Activity names are the durable key; the numeric ID is filled at load. [font face="courier new"]actweight[/font] is the random share among sequences of that activity. Player code classifies movement first, then resolves an activity; walk vs run uses the body's own authored forward-walk speed. NPC selection is schedule/task policy, not recoverable from clip names.

[font size="4"][b]7.4 Movement — piecewise, on the animdesc[/b][/font]

44-byte records, index relative to the animation descriptor. Each [font face="courier new"]position[/font] is cumulative at that record's [font face="courier new"]endframe[/font]. Between records:

[code]
d = v0 * f + 0.5 * (v1 - v0) * f * f
[/code]

[font face="courier new"]v0[/font]/[font face="courier new"]v1[/font] are lengths; block travel is [font face="courier new"]0.5*(v0+v1)[/font]. [font face="courier new"]angle[/font] is 0 on shipped records.

[font face="courier new"]baseballbat_attack_med[/font] lunges mid-clip and ends at cumulative zero. The last record's position is not the runtime question. No records at all makes [font face="courier new"]Studio_AnimMovement[/font] return false.

The clip stays in place. Retail stores ground speed as move-distance / duration once, at sequence select; the motor reads that. Playback rate is not multiplied back in. On a blend-grid travel sequence the four corner motions are pose-weighted once and held. Player applies this from move setup; an NPC only from task arms while [font face="courier new"]MOVETYPE_STEP[/font].

[font size="5"][b]8. Layers and transitions[/b][/font]

[font size="4"][b]8.1 Sequence flags[/b][/font]

[ul type="disc"][li][font face="courier new"]0x1[/font] looping (some looping idles omit it);[/li][li][font face="courier new"]0x2[/font] SNAP: drop the previous-sequence fade set; on an overlay, also zero that slot's blend times;[/li][li][font face="courier new"]0x4[/font] additive;[/li][li][font face="courier new"]0x8[/font] autoplay, weight 1.0, after base and overlays;[/li][li][font face="courier new"]0x10[/font] with [font face="courier new"]0x4[/font]: place the scaled quaternion delta on the right. Shipped named deltas are [font face="courier new"]0x14[/font]: [font face="courier new"]out.rot = normalize(out.rot * scaled_delta)[/font];[/li][li][font face="courier new"]0x100[/font] / [font face="courier new"]0x200[/font] activity-candidate filters;[/li][li][font face="courier new"]0x400[/font] take min rather than max fade — unexercised.[/li][/ul]

Ordinary masked layers interpolate toward the layer pose only for bones they own.

[font size="4"][b]8.2 Autolayers versus overlays[/b][/font]

An autolayer entry is four bytes: a sequence index. No ramp, no pose parameter, no flags. Depth one, at most two children, file order (throwing-star content reverses ordinary-then-delta). Weight is a DLL constant [font face="courier new"]1.0[/font] times the target's binary bone mask. Autolayers nest inside every accumulate: the base and each overlay recurse their own list, which is how an attack overlay brings its aim layer.

Four overlay slots, 48 bytes each. [font face="courier new"]AllocateLayer[/font] takes the lowest zero-weight slot and returns [font face="courier new"]-1[/font] when full. [font face="courier new"]SetLayer[/font] writes weight 0.1 (occupancy), weightMax 1.0, blendIn/Out 0.2. Visible weight then rides the layer's own cycle:

[code]
w = 1
if (blendIn  && cycle < blendIn)      w = cycle / blendIn
if (blendOut && cycle > 1-blendOut)   w = (1-cycle) / blendOut
weight = min(3w² − 2w³, weightMax)
[/code]

Death is weight-zeroing. Weights are clamped to [0,1] and never normalised across slots. [font face="courier new"]m_Flinch[3][/font] is a separate stack (linear ramp, time expiry, per-layer pose-parameter override).

Overlay slots dispatch their own event timelines, including at weight 0. Autolayers never do: nothing reads an autolayer's [font face="courier new"]numevents[/font] unless that sequence is also the base or an overlay. The shipped [font face="courier new"]*_attack_layer[/font] / [font face="courier new"]*_reload_layer[/font] labels therefore also exist as overlays.

[font size="4"][b]8.3 Client transitions[/b][/font]

The client keeps previous sequences and fades them with [font face="courier new"]SimpleSpline(t) = 3t² − 2t³[/font], newest to oldest, no small concurrency cap. Duration is the max of the two sequences' fade values unless SNAP clears the set. The server has no equivalent list, so poses may differ during a fade. The node graph is empty; duration comes from the fade triple at 612.

[font size="5"][b]9. Animation events[/b][/font]

76 bytes: [font face="courier new"]float cycle; int event; int type; char options[64][/font]. [font face="courier new"]type[/font] is 0 and unread. No later [font face="courier new"]szeventindex[/font].

IDs below 5000 are server gameplay: window [font face="courier new"][lastCheck, cycle + 0.1·rate)[/font], wrap once, then the entity's handler. IDs 5000+ are client presentation (muzzle, sound, bodygroup, attachment FX): window [font face="courier new"](prevCycle, cycle][/font], no look-ahead, no wrap. Viewmodels offer events to the associated client weapon first.

An event number copied into a generic notify is not equivalent without that owner split. Melee contact is §7.5, not this table.

[font size="5"][b]11. Split inheritance — bone flag [font face="courier new"]0x2[/font][/b][/font]

On ordinary bipeds, [font face="courier new"]Bip01 Spine1[/font] carries this bit. Hierarchy construction, not the channel decoder:

[code]
root:    world = root_to_world * local
child:   world = parent_world * local
flagged: world.rotation    = root_to_world.rotation * local.rotation
         world.translation = transform_point(parent_world, local.position)
[/code]

The spine takes translation from its parent and rotation from the entity frame. A standing export can look fine and collapse seated. A bake that applies the rule once into tracks does not double-apply: StudioRender never tests the bit, it only reads [font face="courier new"]poseToBone[/font]. Blending first then applying the rule is the retail order; correcting each clip then blending is an approximation.

[font size="5"][b]12. AxisInterp[/b][/font]

[font face="courier new"]Flags &amp; 0x1[/font], [font face="courier new"]ProcType[/font], [font face="courier new"]ProcIndex[/font] (bone-relative). Every shipped rule is type 1, 176 bytes:

[code]

Vector pos[6];

Six signed-axis entries. Position entries are often repeated binds, with real exceptions. [font size="4"][b]14.1 Bone chains — hair, ponytails, breasts[/b][/font]

[font size="4"][b]14.2 Renderer cloth — Jeanette's skirt, Sheriff's coat[/b][/font]

Header flag [font face="courier new"]0x400[/font]. [font face="courier new"]StudioModel[/font] holds an LOD-major definition-offset matrix plus bind-space capsules (36 bytes) and spheres (20 bytes), transformed through the current skin palette; radius is not scaled. [font face="courier new"]StudioMesh[/font] holds three LOD-major maps: byte selector ([font face="courier new"]0xFF[/font] = ordinary skin), [font face="courier new"]u16[/font] position/normal index (high bit flips the normal), [font face="courier new"]u16[/font] tangent index (read only when selected).

Extent is [font face="courier new"]NumVertices × VTX numLODs[/font]. Goth is 4 definition rows / 7 VTX LODs and stores all seven. Doppleganger truncates the tangent payload where the remaining selectors are [font face="courier new"]0xFF[/font].

A definition has pinned and dynamic particles, distance constraints, compression-only constraints, collision triangles at stride 6 ([font face="courier new"]uint16[3][/font]; a leftover u16 after the last triangle is alignment residue), and tangent/normal reconstruction. Pinned particles refresh from skinned source vertices; dynamic particles integrate in double-buffered state. Only selected vertices are substituted.

[font size="5"][b]15. Face[/b][/font]

Facial arrays begin at header 344. A standard speaking face: 65 flex descriptions, 44 controllers, 60 RPN rules.

Ops: [font face="courier new"]CONST FETCH1 FETCH2 ADD SUB MUL DIV[/font]. The operand dword is a union: float bits for [font face="courier new"]CONST[/font], integer index for the fetches, ignored for arithmetic. Projecting both views manufactures NaNs from patterns such as [font face="courier new"]0xffffffff[/font].

[font face="courier new"]FETCH1[/font] is a controller index. [font face="courier new"]FETCH2[/font] is a flexdesc index into the array previous rules are filling, so order is load-bearing. [font face="courier new"]DIV[/font] uses a zero guard; a shipped rule divides by [font face="courier new"]right_open[/font]. Three standard rules take right-side inputs where their names suggest left; that is authored. Retail loads [font face="courier new"].vfe[/font], not the companion [font face="courier new"].txt[/font].

Compressed morph, 8 bytes: vertex index, two renderer-table offsets, two magnitudes.

[code]
position_delta = direction * (magnitude / 255) * 8
normal_delta   = direction * (magnitude / 255) * 2
[/code]

Ming Xiao's transformation uses a 20-byte raw form (float position delta, table-encoded normal). A flex-description name is not geometry; [font face="courier new"]StudioFlex[/font] records on meshes are.

Eyes: two 140-byte [font face="courier new"]StudioEyeball[/font] on speaking characters and most player bodies. Eye meshes have [font face="courier new"]materialtype == 1[/font]. The first 16 flex descriptions are eyelid ramps; the renderer aims the iris and then overwrites those four slots. Targets are linear offsets through [font face="courier new"]asin(target/radius)[/font]. Blink is a 0.3 s envelope after networked interpolation. Player bodies have eyes and no flex rig: still face, live irises.

The 20-byte mouth record names a jaw bone and flexdesc [font face="courier new"]mouth[/font]. Retail writes audio amplitude there after rules. That flexdesc has no deforming records and is not read by [font face="courier new"]FETCH2[/font] — a readout, not a driver.

[font face="courier new"].lip[/font]: the leading integer is the lookup key; the printed phoneme string is not unique. [font face="courier new"]WORD[/font] rows contain quotes and legacy punctuation. Runtime selects [font face="courier new"]<stem>_phonemes.vfe[/font] or [font face="courier new"]<stem>_expressions.vfe[/font] from the actor model; the path inside the VFE is provenance.

VFE header: [font face="courier new"]EFV\0[/font], version, 128-byte name, length, flex-setting count. Phonemes ramp in [b]before[/b] their authored start; blend width is the header's two phoneme-filter floats.

Order: network/choreography → phonemes → blink → file-order rules → mouth amplitude → eye/eyelid write-back.

[font size="5"][b]16. Viewmodels and wielded weapons[/b][/font]

Bloodlines never merges a held weapon into the wearer. First person and third person each use two studio models, under different contracts.

[font size="4"][b]16.1 First person — two viewmodel entities[/b][/font]

Clan/gender hands: 42-bone [font face="courier new"]Camera01[/font] rig, shared firearm and lockpick bank, no melee. [font face="courier new"]camera_class melee[/font] is the force-third bit (same as [font face="courier new"]force_3rd[/font]). Compact weapon viewmodels carry the visible gun on a subset rig. The player owns two slots; the server assigns matching sequence and playback to both.

Hide is submission-only. Both entities keep model, sequence, cycle, and palette in third person. The first frame of a first-to-third request cuts them immediately.

[font size="4"][b]16.2 Third person — follow by bone name[/b][/font]

Item roles, not interchangeable:

[ul type="disc"][li][font face="courier new"]viewmodel[/font] — first person ([font face="courier new"]view/v_[/font]);[/li][li][font face="courier new"]playermodel[/font] — loose ground mesh ([font face="courier new"]world/g_[/font]), [b]not[/b] what a character holds;[/li][li][font face="courier new"]wieldmodel_m/_f[/font] — held mesh ([font face="courier new"]wield/w_[/font]);[/li][li][font face="courier new"]infomodel[/font] — inventory ([font face="courier new"]info/i_[/font]).[/li][/ul]

[font face="courier new"]w_null.mdl[/font] is a real zero-bone, zero-vertex model. Equip applies the named string unconditionally, so keys and armour take the same path as a katana and draw nothing. Empty string is a different value (“leave the current model”).

Equip sets [font face="courier new"]MOVETYPE_FOLLOW[/font] (0xb) and [font face="courier new"]SetAimEnt[/font] (wearer). Detach sets [font face="courier new"]MOVETYPE_TOSS[/font] (6) and clears the aim entity. [font face="courier new"]0xc[/font] is [font face="courier new"]MOVETYPE_CARRIED[/font] (origin only). The sibling call is [font face="courier new"]SetOwnerEntity[/font], not a move parent.

Holster leaves that binding intact and [font face="courier new"]Hide()[/font]s. An active-weapon switch is holster-then-deploy, not detach-then-equip. First person only suppresses world-weapon submission; NPC weapons ignore the player's camera.

Client merge copies by case-insensitive name with no flag filter:

[code]
for each weapon bone:
    if a parent bone has the same name:
        copy the parent's 3x4 world matrix
    else:
        boneToWorld[i] = boneToWorld[parent[i]] * localPose[i]
[/code]

[font face="courier new"]localPose[/font] is this weapon entity's decoded sequence, not bind. Most wield models carry one [font face="courier new"]idle01[/font] / [font face="courier new"]ACT_VM_IDLE[/font]; some hold a constant pose that is not bind (more than a foot on a flamethrower).

The server merge additionally requires [font face="courier new"]leaderBone.flags &amp; 0x0C[/font]. The seven unskinned prop bones ([font face="courier new"]Bat[/font], [font face="courier new"]bush hook[/font], [font face="courier new"]handle[/font], [font face="courier new"]gerber[/font], [font face="courier new"]Sledgehammer[/font], [font face="courier new"]Cylinder01[/font], [font face="courier new"]tire iron[/font]) read [font face="courier new"]0xfff0[/font], so the server matches at the hand instead. A server [font face="courier new"]GetAttachment[/font] mid-swing does not agree with the drawn frame. Those seven bones exist as animation targets; melee and stealth-kill clips move them, locomotion does not. Firearm mounts match no character bone and ride the hand by the unmatched rule.

Grip is whichever hand the skinned chain descends from (bush hook, sledgehammer, fire axe, lockpick are left). Melee bind agreement is per-sex and exact, except [font face="courier new"]w_f_bushhook.mdl[/font], whose [font face="courier new"]bush hook[/font] bind is a literal identity — the two sexes disagree by about 36 inches.

[font face="courier new"]w_{m,f}_handleclaws.mdl[/font] ships its own claw sequences. Only six bodies declare all thirty skinned names; on any other wearer most of that skeleton runs on those clips.

A weapon's moving part can survive into the wield file and never play there. The Ithaca M37 viewmodel animates a 117-influence pump; the wield model has the same bone, one idle clip, and a pump that never cycles in third person.

[font face="courier new"]anim_prefix[/font] is copied into [font face="courier new"]m_szAnimExtension[/font] and otherwise unread. Bloodlines replaced HL2's sequence-name extension with per-class activity tables and left the string in place (fire axe → [font face="courier new"]sledgehammer[/font], 157 items author a single space).

[font face="courier new"]item_g_stake[/font] authors no wield model. The only geometry declaring [font face="courier new"]Cylinder01[/font] is [font face="courier new"]character/shared/{male,female}/stake.mdl[/font], a full hand rig no item references. The caller that selects it is open.

NPC carriage uses the same item keys ([font face="courier new"]additionalequipment[/font]). Firearms come from per-placement keyfields, not a starting-equipment package.

  → hierarchy with split inheritance

  → cloth substitution on selected vertices

  → FOLLOW + m_hAimEnt

playing sequence envelopes (NPC select) and 188-byte contacts

  → combo by sequence label in the authored window
[/code]

A compiler must emit every count/index pair, the three vertex formats, VTX, the melee block, includes, flex, cloth, and sibling checksums, and reject malformed topology rather than a plausible-looking file. Retail playback is required and not sufficient.
